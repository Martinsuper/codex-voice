# 架构与重构路线

本文记录当前工作区的运行边界，作为逐步重构的基线；协议和状态说明以代码为准，改动时需同步更新。

## 运行路径

```text
Codex hooks / OpenCode → 收件箱、事件文件 → Python 引擎
                                            ↓ 状态及设备命令（逐行 JSON）
macOS 界面 ← Swift 应用与引擎进程 ←─────────┘
                   ↓ 用户命令（管道；部分提醒操作通过收件箱持久化）
             Passport BLE / Piko 网络 → 设备
                   ↓ 听写音频
              本机语音识别 → 当前输入框
```

Python 引擎负责事件适配、提醒规则、播报调度和恢复；Swift 负责应用生命周期、界面、配件连接及本机听写。设备协议由各传输实现处理，固件有独立构建与验证流程。

Python 的 `voice_engine.py` 负责提醒引擎并保留兼容入口，`engine_runtime.py` 管理进程循环和持久化，`event_adapters.py` 转换 Hook 和 OpenCode 事件，`rollout_adapter.py` 读取 Codex 本地事件，`speaker.py` 负责电脑和配件的播报路由。Swift 的 `EngineMessages.swift` 负责引擎输出的逐行 JSON 分帧和消息分类，`EngineProcess.swift` 构造引擎进程及管道，`EngineRecovery.swift` 集中应用的引擎启动与恢复方法；恢复状态仍由应用持有。Passport 和 Piko 通过共同的命令接收接口接入；具体连接、配对和传输仍由各自实现。

## 状态归属

| 状态 | 当前权威来源 | 持久化或传播 |
| --- | --- | --- |
| 提醒、暂停和播报状态 | Python Engine | 快照推送给 Swift；恢复数据写入 `reminder-state.json` |
| 提醒和语音设置 | Python 引擎设置 | `settings.json`；Swift 显示引擎快照 |
| 账号用量 | Python UsageMonitor | 快照包含用量；低额度提醒记录在 `usage-low-alerts.json` |
| 窗口及面板状态 | Swift 应用 | `panel-state.json` 用于记录面板状态 |
| 配件连接与听写会话 | Swift 配件服务 | 状态与设备同步；听写会话在进程内 |
| 宠物资源 | 来源与转换缓存、设备存储 | 通过设备资源传输协议同步 |

运行目录还包含 `status.json` 快照、`engine.lock` 和 `inbox/`。这些文件不是同一种状态：收件箱是命令交付路径，快照供读取，锁用于进程协调。

## 进程协议现状

Swift 向引擎标准输入写入每行一个 JSON 对象；引擎标准输出以同样格式返回快照、`error` 或 `passportCommand`。管道读取可以拆分任意字节，接收端须在换行后解析；非 JSON 对象或缺少提醒数组的快照会被忽略，避免异常消息清空界面。单行上限为 8 MiB，超限行会丢弃至下一个换行符，后续消息仍可处理；引擎启动时重置接收缓冲。提醒操作 `ack`、`ack_all`、`resolve`、`snooze` 使用收件箱文件，并附带发送时间及已知提醒 ID，以支持恢复。设备命令按 transport 路由。

目前内部协议没有统一的版本协商，也未为全部消息定义静态类型。协议演进应先增加兼容测试，再增量引入类型和版本；不要同时破坏已有收件箱、进程和设备格式。

## 分阶段计划

1. 建立测试、打包和设备验证基线，记录未覆盖的真实设备场景。
2. 固定跨进程与设备消息契约，分离编解码和传输；为兼容性、断连和恢复增加针对性测试。
3. 将 Python 事件适配、提醒决策、输出调度和持久化逐步分离，以现有行为测试保护迁移。
4. 分离 Swift 的进程生命周期、引擎客户端、界面状态和窗口协调。
5. 根据实际能力提取设备接口，保留各设备的传输、配对及协议实现。
6. 梳理错误反馈、日志、配置迁移及目录，完成端到端和真实设备验收。

每个阶段应保持可运行，真实 BLE、音频和设备验证不能由主机模拟测试替代。
